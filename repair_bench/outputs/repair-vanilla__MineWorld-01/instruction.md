# repair-vanilla__MineWorld-01 · 像素方块世界 (MineWorld) 修复任务

## 你拿到的交付面 / The face you get

一个**零构建**的原生 ES Module 3D 体素沙盒（浏览器里的迷你 Minecraft）：程序化生成的区块地形（沙、土、石、水、树），出生点正对着一座由 9×9 点阵字母拼成的 DENSITY 立墙，第一人称角色控制与碰撞，六格物品栏（数字键与滚轮选择）、方块名称提示、距离雾与三盏灯光、视野调节（带屏幕提示）、调试面板、暂停界面、移动端触控路径，以及散布在地形上的小机器人。界面文案是简体中文（`lang="zh-CN"`），立墙拼的是拉丁词 DENSITY。

树下没有 package manifest、没有依赖目录、没有打包器、没有 TypeScript、没有任何测试装置：源码根目录下的入口文档**就是**交付物本身。三维库已随树提供（本地 vendor 副本），因此**运行期零网络**。

## 运行方式 / How the face is served

- 页面用 ES Module ＋ importmap，**必须经 HTTP 服务打开**（直接用 `file://` 打不开，这是模块规范而不是缺陷）。判分器已经用静态服务把源码根目录serve在回环口上。
- 零构建：`--install-cmd 'true'` · `--build-cmd 'true'` · `--outdir .`。不要引入构建步骤、不要新增依赖、不要改动交付面的离线自足性。
- 视口固定 1280×720（桌面路径）。移动端触控分支存在但不是本次被测面。

## 关于这些报告 / About these reports

- **并非所有缺陷都有报告提及 / Not every defect is reported.** 上面 9 条里有一部分描述的是**本来就该这样的正常行为**（照单去“修”它会破坏出厂行为，并被判分惩罚），而另一些真实缺陷**根本没有出现在报告里**——你需要自己把整个交付面读一遍，找出所有偏离出厂行为的地方。
- 报告是**症状**，不是诊断：它们描述玩家在屏幕上看到的东西，不会告诉你涉及哪个文件、哪一行、哪种机制，也不会告诉你应该改什么。
- 判分是**全有或全无**：既要修好全部真实缺陷，也要保证出厂行为一处都不被破坏（包括那两条假报告描述的正常行为）。
- 有缺陷之间存在**互相掩盖**关系：某一处错误可能让另一处错误在屏幕上看不出来。修掉其中一处之后，被掩盖的那一处才会显形——所以“看起来对了”不等于“对了”，请以代码与状态为准。
- 至少有一处缺陷是**时间相关**的：只在某个时间窗口里能观察到，页面刚加载时的快照看不出问题。

## 约束 / Constraints

- 运行期**零网络**：不得引入任何外部 URL、CDN、远端 API 或字体/图标外链；所有资源必须来自树内。
- 保持零构建与源码根即交付物的形态；不要新增打包产物、不要把交付面改成需要编译的结构。
- 不要删除或改写页面上已有的 `data-testid` 属性与只读校验句柄（判分面依赖它们；它们是纯读的，不会给你写状态的机会）。
- 不要通过写全局变量、写 storage、改 URL 或给判分句柄打补丁的方式“让检查点变绿”：这些残留会被专门检查。

## 判分 / Grading

35 个检查点，分成两个分区：12 个 F2P（每个对应一处真实缺陷的独占探测器）与 23 个 P2P（出厂行为守卫，包含假报告的绿守卫、离线自足守卫、状态隔离守卫与时序钉子）。reward = 1.0 当且仅当两个分区全绿；score = 100 × f2p_rate × p2p_rate。
