# 修复任务：facebook-clone（React + TypeScript + Vite + Tailwind 的社交站前端克隆）

## 1. 你拿到的是什么

一个纯前端的社交站界面克隆（上游 `saifulshihab/facebook-clone`，master 分支）。技术栈是 React 18 + TypeScript + Vite，样式用 Tailwind，路由是 BrowserRouter 的真实路径（`/`、`/reel`、`/marketplace`、`/group`、`/login`、`/stories/:id`）。**没有后端**：所有内容都来自仓库里自带的静态数据集，登录也不是真的登录墙（进入任何页面都不需要凭据）。

这份代码在交给你之前被注入了 **12 处缺陷**。它们全部是**行为缺陷**——代码能编译、能构建、页面能渲染，看不出报错，但交互起来的读数不对。你的任务是把这 12 处全部修回正确行为。

构建与自检（判分环境**无网络**，依赖树已随包提供）：

```
npm run build      # 逐字是 tsc && vite build —— 类型检查是构建的一部分，任何 TS 报错都会让构建失败
```

产物目录是 `dist`，用任意静态服务器挂载它即可（需要 SPA 回落，因为深链在磁盘上没有对应文件）。

## 2. 用户报告（共 9 份）

下面是测试同学和用户提交的报告。**其中 7 份对应真实缺陷，2 份描述的是本来就该如此的正常行为**（见每份报告后的标注——但你拿到的版本里不会有标注，需要你自己判断）。

**报告 ①** 「短视频那个竖屏页面，往下翻不动了。滚轮滚了、右下角那个向下的箭头也点了，画面就是死死停在第一条，作者名字和右边的点赞/评论/分享数字从来不变。往上翻的箭头一直是灰的，这个我理解，因为本来就在第一条。」

**报告 ②** 「还是那个竖屏页面。就算能翻下去，右边那一列数字也不对：四位数的点赞量不再被缩写成「几点几 K」那种紧凑形式了，而是把原始数字整串摊出来，把那一列挤得很宽。三位数的显示倒是正常。」

**报告 ③** 「首页顶部那排 story 圆圈，一进页面最左边就挂着一个向左的箭头。可它已经在最左端了，根本没法再往左滚——这个箭头应该等我真的往右滚过之后才出现。」

**报告 ④** 「群组页的长帖子不折叠了。以前超过一定长度会截断、底下挂一个 `See more`，现在整篇原样铺出来，`See more` 按钮一个都不剩。短帖子没变化。」

**报告 ⑤** 「点开某条帖子的详情弹窗，点 `View all 1 reply` 能把回复展开，这个正常。但再点一次收不回去了——按钮文字卡在 `Hide replies`，回复也一直在。以前是开合开合来回切的。」

**报告 ⑥** 「登录页的红色校验提示出现得太早。我鼠标刚在邮箱框里点了一下、什么都还没输（或者输了一个字符又删掉），**还没离开输入框**，底下就已经挂着两条红字了。以前必须等失焦之后才提示。」

**报告 ⑦** 「登录页那颗主按钮和它下面的 `Create New Account` 按钮都变矮了一截，看着像被降级成了小尺寸按钮。旁边两个输入框的高度倒是没变。」

**报告 ⑧** 「首页长帖子点 `See more` 没反应——按钮文字确实变成了 `See less`，可正文还是被截断的、末尾还挂着省略号。点了跟没点一样。」

**报告 ⑨** 「竖屏页那个 `Follow` 按钮，点下去文字不会变成 `Following`；还有首页帖子的 `Like`，点了点赞数也不加。这两个是不是也坏了？」

> 🔴 关于报告 ⑨：**这是正常行为，不要"修"它。** 这个克隆把这两处做成了纯静态演示件——`Follow` 没有绑定任何关注状态，`Like` 也不改计数。它们本来就不会变。如果你给它们加上状态让它们"响应"，判分会认为你破坏了既有行为。报告 ⑨ 存在的意义就是考验你能不能分辨"用户以为坏了"和"真的坏了"。

## 3. 🔴 并非所有缺陷都有报告提及

上面 9 份报告只覆盖了 12 处缺陷中的一部分。**并非所有缺陷都有报告提及**——有若干处缺陷没有任何用户报告对应，它们在这个应用里是**静默的**：不报错、不报警、页面看着也完整，只有你真的去点那一下、真的把读数和「这个组件按代码本意应该输出什么」对照起来，才会发现不对。这类未报告的缺陷同样计入判分。

所以：**读源码，不要停在报告清单上。** 建议把每一条路由都走一遍，把每一个可交互元素都点一次（包括那些看起来「显然没问题」的），并且对每处交互都想清楚「按这份代码的本意，这一步之后应该是什么状态」。报告是线索，不是边界。

## 4. 判分口径

判分在一个无头浏览器里进行：1280x720、locale en-US、时区 UTC，**每一次测量各自一个全新的浏览上下文**——所以存储、地址栏、下拉框的开合状态都不会从一次测量带到下一次。所有读数都取自**运行中的应用**，不是取自源码文本。

检查点分两个分区：

- **应转绿分区**：对应 12 处缺陷各自的载体行为。交付给你的代码里这些全是红的；全部修好后应全部转绿。
- **应保持绿分区**：领地守卫与正常行为守卫。它们在交付态就是绿的，修完之后**必须仍然是绿的**。如果你为了修某一处而破坏了它周边的既有行为（把组件删掉、把某个交互禁用掉、把静态文案改掉、把某条路径整个绕开），这一分区就会翻红，判分直接归零。

两个分区全绿才算修复成功。**只让第一分区变绿、同时让第二分区翻红，不得分。**

另外几条硬性纪律：

1. **修的是机制，不是读数。** 不要写死判分要读的那个值。检查点会同时核验浏览器存储（localStorage / sessionStorage）保持为空、页面全局作用域上没有多出来的人为标志位、以及地址栏没有被人为改写。「检测到在被测就走另一条分支」或「往全局挂一个已修复标志」这类做法会被判为作弊。
2. **不要靠削弱或删除既有功能来消除症状。** 领地守卫会核验相关组件的结构、数量、静态文案与相邻交互都还在。
3. **构建必须保持通过。** 类型检查是构建的一部分：改完之后 `npm run build` 必须仍然 rc=0。留下一枚编译不过的树等同于没有交付。
4. **不要动离线适配。** 这份代码已经为「无网络」环境做过适配（远端占位图、远端图标样式表、远端样片视频都已本地化或摘除）。不要把任何东西重新指回外部主机，也不要新增网络调用。

## 5. 交付

直接在这份代码上改。不需要写测试，不需要改构建配置，不需要升级依赖。改完请自己跑一遍 `npm run build` 确认通过，再把 `dist` 挂起来逐页点一遍。
