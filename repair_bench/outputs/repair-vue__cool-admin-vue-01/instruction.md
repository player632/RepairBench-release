# Repair Task - cool-admin-vue, a Vue 3 + TypeScript admin framework and its demo app

You are working on the source code of **cool-admin-vue**, the front end of an open-source
administration framework built on Vue 3, TypeScript, element-plus, pinia, vue-router, tailwindcss
and i18n, bundled by Vite. The repository is not a component gallery: it is a working back-office
shell - a login page, a persistent layout with a collapsible side menu, a top bar, a tab bar that
keeps opened pages alive, and a set of demonstration modules that exercise the framework's own
CRUD generator, its dictionary service, its theme store, its internationalisation switch and its
upload/excel/dev-tools plugins. Routes are addressed with real paths (history mode), so a page is
reached at `/demo/crud` rather than behind a hash, and the menu that fills the sidebar is fetched
at boot and turned into routes dynamically.

Four areas of it matter for this task, and they are wired into one small economy:

- The **shell**: a login surface, then a layout whose left menu comes from the server, whose top
  bar carries a user dropdown, a language dropdown and a theme drawer, and whose tab bar keeps one
  active tab, can close any tab, and has a refresh button that re-creates the cached page.
- The **dashboard** (`/`): a row of animated counters - total users, page views, payments, total
  sales - plus a hot-goods ranking and a category chart.
- The **CRUD demonstration page** (`/demo/crud`): seven tabs, each a card wall of small previews
  generated by the framework's own CRUD builder. One of those cards opens a dialog with a table of
  nine people whose columns are resolved through the dictionary service.
- The **dynamic-route demonstration page** (`/demo/test/route/:id/:name?`): a page that reads the
  two path segments the router hands it and renders them.

The whole data plane is served inside the browser: the project is fully offline and every request
the application makes is answered by a deterministic in-page fixture layer, so the menus, the user
session, the dictionaries and the demo tables all come from that fixture and nothing is fetched
from a network. Your work is stored in the browser between visits, including the session token and
its own expiry stamp, the chosen theme and the chosen language.

Because the machine has no network access, a few things are degraded or fixed on purpose and are
**not** defects:

- Every number on the dashboard that upstream draws at random is drawn from a **seeded** generator
  instead, so the same build shows the same figures on every load. The values themselves are still
  animated and still count up from zero; only their source is deterministic.
- One decorative icon font that upstream imports from a third-party content delivery network is not
  loaded. A few developer-tool icons therefore render without their glyph. Nothing else uses that
  font.
- The build-time configuration points the project's development proxy at an address that can never
  be served, so the build never depends on a back end being up. This changes no runtime behaviour.
- The framework's plugin-marketplace and helper views are not reachable from the menu fixture,
  because upstream they call a remote service. They are still on disk and still compile.
- One committed build input directory at the project root, which holds the generated service
  description the build reads, must stay: it is an input to the build, not an output of it.
- The project ships **no** test suite, no test runner configuration and no test script, so there is
  nothing to remove and nothing to run.

QA collected a batch of user reports about this build. They are quoted below roughly as users wrote
them - with their own steps, noise and assumptions. Treat them as starting points, not as
diagnoses:

- Most reports describe real, reproducible defects, each with its own root cause somewhere in the
  codebase. The root cause may sit in a different module than the one the symptom appears in, and
  may be on a different page altogether from where you notice it.
- At least one report describes behavior that is actually intended; verify a report before changing
  anything because of it.
- Not every defect is necessarily mentioned in the reports. Behaviors you break while fixing other
  things still count against you.
- Do not remove, rename or repurpose any data-testid attributes - they are verification probes
  required by the checker.

The reports, in no particular order:

1. I am not sure a login ever runs out any more. I left a session sitting well past the point where
   it should have lapsed and then clicked around - the app just carried on as if nothing had
   expired, and it never once quietly topped my session up the way it used to. It is as if the whole
   "your session has run out" path has gone to sleep.

2. The colour scheme looks washed out. The main brand colour is exactly right, but everything
   derived from it - the lighter shades that show up on hover, on disabled buttons and on pale
   backgrounds - comes out far paler than it should, almost white. Pick a shade three steps up from
   the brand colour and compare it with the old build and you will see what I mean.

3. On the CRUD demonstration page there is a card that opens a preview dialog with a table of nine
   people, and the column that says what each of them does for a living is completely empty - all
   nine rows, every single one. The names, the phone numbers, the grades, the status and the dates
   next to it are all fine. It is only that one column that renders nothing at all.

4. When I pick one of the tabs along the top of the CRUD page, then leave for another page and come
   back through the tab bar, the page has quietly reset itself to the first tab. The address bar
   still shows the tab I chose, so it looks like my choice was written down somewhere - it just is
   never read back.

5. The little cross on a tab closes the wrong one. I had two tabs open, I clicked the cross on the
   one I was NOT looking at, and it closed the tab I WAS on and dropped me onto a different page.
   The tab I meant to close is still sitting there untouched.

6. When I choose one of the recommended colour themes from the drawer on the right, the accent
   colour does change, but the rest of the look never follows it - the parts of the layout that are
   supposed to restyle along with the theme just stay as they were. And when I come back later the
   theme I picked is still the selected one, so it was recorded.

7. I switched the interface to English from the language dropdown in the top bar. The page flickers
   and comes back in Chinese. Traditional Chinese does exactly the same. It never sticks, not even
   after I reload by hand.

8. After I sign out, I can still see a refresh credential for my account sitting in the browser's
   stored data. Everything else about me is gone and I am back at the login page, but that one entry
   stays. Is that a leak? Shouldn't signing out wipe the lot?

9. The CRUD demonstration page looks broken to me. It has dozens of little cards but not a single
   table anywhere on it - and this is the page named after creating, reading, updating and deleting
   rows. Surely it should be showing a table?

## Constraints

- Do not run the project's build, dev server or tests to verify yourself during the session; a
  separate verifier rebuilds and drives the app. Focus on reading the code and fixing root causes.
- The app is offline. Do not add a network call, a remote asset, a CDN script or a webfont: nothing
  will resolve, and the checker measures that the delivered build issues no cross-origin request.
- Fix root causes, not symptoms. A fix that special-cases one page, one probe or one value, that
  hard-codes an expected figure, or that reaches into the browser's stored state to fake a result
  will be caught: the checker verifies that the app leaves no residue behind, that its observation
  surface cannot be re-pointed, and that behaviors which are correct today stay correct.
- Do not "clean up" the seeded dashboard figures, the missing icon font, the dead development
  proxy, the unreachable marketplace views or the committed build-input directory. Those are
  declared above and each one is guarded.
